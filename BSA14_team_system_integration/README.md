# BSA14 — Интеграция систем

## О проекте

Проект о той части работы аналитика, которая начинается там, где заканчивается работа с одной системой, — на стыке между системами. На кейсе «Доставка заказов» выделены все информационные потоки сервиса, для каждого определены мастер-система и система-получатель, описан словарь данных, спроектирован сценарий интеграции и рассчитаны требования к объёму, частоте и срокам передачи данных.

---

## Что было сделано

- `ex00.ods`  
  Выделение потоков данных сервиса доставки (командная часть проекта).  
  Определено 9 потоков — от получения заказов партнёров и списка точек комплектации до передачи данных в бухгалтерию и обработки команд диспетчера, для каждого указаны название, назначение и направление (в систему / из системы).

- `ex01.ods`  
  Определение мастер-систем для входящих потоков.  
  Для каждого потока рассмотрены возможные источники данных в окружении (CRM и ERP партнёра, мобильное приложение курьера, бухгалтерская система, веб-интерфейс диспетчера) и обосновано, какая из систем является первоисточником — например, статус заказа считается официальным только после подтверждения через собственное мобильное приложение курьера.

- `ex02_recepients.ods`, `ex02_consistency.ods`  
  Определение систем-получателей для исходящих потоков и проверка согласованности с мастер-системами.  
  Для каждого исходящего потока выбрана и обоснована система-получатель (бухгалтерская система, мобильное приложение курьера), а для связанных пар «исходящий → входящий» подтверждено полное соответствие — например, цикл «данные для бухгалтерии (курьеры)» → «данные о начисленной оплате» замыкается на одной и той же бухгалтерской системе.

- `ex03.ods`  
  Словарь данных для всех 9 потоков.  
  Для каждого потока описаны блоки данных с учётом вложенности (order, customer, pickup_address, items[] и др.), а для каждого атрибута — тип данных, длина, обязательность и ограничения (например, формат телефона, уникальность order_id, обязательное условие «время доставки в будущем»).

- `ex04.odt`  
  Сценарии интеграции UC-INT-01 – UC-INT-09 в формате Коберна для каждого из 9 потоков.  
  Для каждого сценария описаны действующее лицо, цель, предусловия, триггер, основной и альтернативные потоки, постусловия, а также обоснован рекомендуемый стиль интеграции — синхронный REST-вызов для приёма заказа от партнёра и обновления статуса курьером, обмен файлами для регулярной выгрузки в бухгалтерию, обмен сообщениями для точечных финансовых событий.

- `ex05.ods`  
  Требования к объёму и количеству сообщений по каждому потоку.  
  Рассчитаны среднее и пиковое количество сообщений в час, средний и максимальный размер сообщения, а также периоды пиковой нагрузки — обеденное и вечернее время, пересменка курьеров, закрытие месяца для бухгалтерских выгрузок.

- `ex06.ods`  
  Требования к частоте и срокам передачи данных.  
  Для каждого потока определены желаемая частота и сроки доставки в штатном режиме, а также допустимые максимальные и минимальные значения — от передачи заказа партнёра в реальном времени (не более 2 секунд) до ночной пакетной выгрузки в бухгалтерию раз в сутки.

---

## Итоги

Работа над модулем показала, что выбор способа интеграции — это не техническое решение архитектора «из воздуха», а прямое следствие бизнес-контекста: критичности потока, его объёма, допустимой задержки и того, кто на самом деле владеет данными. Девять на первый взгляд похожих потоков в итоге получили девять разных профилей требований — от мгновенного синхронного вызова при приёме заказа до неторопливой ночной выгрузки отчёта в бухгалтерию, — и для каждого сформирован полный пакет данных, достаточный для передачи архитектору.
